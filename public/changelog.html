🔬 De "fake" a real · cada servei es prova de veritat
  • Abans (v48): la status page només mirava si la variable d'entorn existia. No provava si el servei realment responia
  • Ara (v49): cada servei fa una trucada real i mesura el response time:
    • SMTP · transporter.verify() de Nodemailer connecta amb el servidor de correu real
    • Anthropic IA · fa una crida real a POST /v1/messages amb 1 token (cost ~$0.0001/dia)
    • Google Calendar · fetch a discovery/v1/apis/calendar/v3/rest + recompte de tokens guardats
    • Base de dades · escriu + llegeix una key de test (verifica integritat read/write)
    • Web/API · monitorea la RSS memory del procés (degradat >800MB, caigut >1500MB)
  • Cada check té timeout (5-6s) i captura errors → si Anthropic falla, veuràs "Auth failed" o el codi HTTP real
⏱ Cron cada 2 min + cache
  • Els checks s'executen en background cada 2 min (no a cada request /api/status)
  • Resultats cachejats a health_status.json (últim) + health_history.json (rolling 30 dies, ~21600 snapshots)
  • /api/status retorna el resultat cachejat instantàniament + indica quan va ser l'última prova
  • Primer check 5s després del boot (deixa estabilitzar variables d'entorn)
📈 Uptime 90 dies basat en historial real
  • Cada snapshot del historial conté l'estat de tots els serveis en aquell moment
  • L'uptime diari es calcula com (snaps_OK / total_snaps) × 100 per dia
  • Es combina amb els incidents (per a manteniments programats) per donar la xifra final
  • Dies sense dades es marquen com no_data (gris) en lloc de fer-se passar per 100% operational
🎨 UI millorada de la status page
  • Cada servei mostra el response time real (ex: 284ms) en JetBrains Mono
  • Si un check falla, el missatge d'error es mostra en vermell sota el nom del servei
  • Memòria RSS del procés visible sota Web/API
  • Comptador de tokens Google guardats sota el servei Google Calendar
  • Header indica "última prova fa X" amb timestamp del cron
🛠 Nous endpoints
  • POST /api/admin/health/recheck · força un re-check ara mateix (útil després de canviar config SMTP/AI)
  • Nou mòdul lib/healthChecks.js reutilitzable

Fases de manteniment persistents · zero-flash al recarregar
💾 Estat del countdown i fases cachejat a localStorage
  • Símptoma anterior: en recarregar /maintenance, les fases tornaven momentàniament a 0% fins que el fetch /api/admin/maintenance responia (flash visual de ~200ms-1s)
  • Ara desem l'estat de manteniment (endsAt, activatedAt, message, active) a localStorage (clau gesem_maint_state_v1) cada cop que el servidor respon
  • Al carregar la pàgina, abans del fetch, llegim aquesta cache i pintem les fases immediatament al % correcte basant-nos en (now - activatedAt) / (endsAt - activatedAt)
  • La cache es considera vàlida fins a 5 min després del moment endsAt previst; si el manteniment ja s'ha desactivat (active=false), s'esborra automàticament
⏱ Fake-progress ancorat a activatedAt (no més reset al refrescar)
  • Símptoma anterior: si NO hi havia endsAt configurat a /admin, les fases avançaven 1% cada 8s amb un comptador en memòria. Recarregar la pàgina = tornar a 0%
  • Ara, sense endsAt, calculem el progrés com (now − activatedAt) / 30min, capant a 95%
  • Resultat: el % és determinístic i depèn només del temps real transcorregut des de l'activació. Recarregar la pàgina manté exactament el mateix progrés
  • Tick de 1s en lloc dels 8s anteriors → progressió molt més fluïda
🎯 Sincronia 100% amb el countdown
  • Cada segon, el mateix tick que actualitza els nombres del countdown (HH:MM:SS) recalcula també el % de les fases
  • Quan el countdown arriba a 00:00:00, totes les fases passen a done alhora amb l'animació de celebració
  • L'estat es preserva entre recàrregues → l'experiència és contínua tot i refrescar

Auto-desactivar manteniment + Stepper de fases redissenyat
🤖 Auto-disable del manteniment al final del countdown
  • Quan defineixes una hora prevista (endsAt) a /admin i s'arriba al moment, el manteniment es desactiva automàticament sense intervenció
  • 3 capes de defensa per garantir que mai oblidem desactivar-lo:
    • Middleware: cada request HTTP comprova si endsAt ha passat i desactiva al moment
    • Endpoint poll: GET /api/admin/maintenance (que la pàgina /maintenance crida cada 30s) també detecta i auto-desactiva
    • Cron intern: cada 20 segons, un timer al servidor comprova i desactiva si cal
  • Resultat: encara que tothom estigui de vacances, l'app es desbloqueja sola a l'hora exacta. La pàgina /maintenance al detectar-ho mostra l'animació "Operativa de nou!" i redirigeix l'usuari a /peticio
🎨 Stepper de fases completament redissenyat
  • Les 4 fases del manteniment ara són un stepper modern amb:
    • Cercles 44px connectats per una línia base gris
    • Línia de progrés verda que creix gradualment segons el % del countdown
    • Fase "done": cercle ple verd amb checkmark blanc + glow subtil
    • Fase "active": cercle ambre amb halo pulsant + emoji girant
    • Fase "pending": cercle gris esmorteït amb emoji al 30% opacitat

  • Celebració al final: quan totes les fases passen a done (countdown=0), s'aplica una animació de scale cascading
  • Si NO hi ha countdown configurat, les fases simulen una progressió lenta automàtica (1% cada 8s) per no quedar-se sempre quietes

  • Nou helper updatePhases(progressPct) que llegeix els data-threshold i pinta cada fase
  • CSS variable --phases-progress per la línia de progrés (transició suau 0.8s)
